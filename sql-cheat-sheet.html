What is SQL and why learn it?

SQL (Structured Query Language) is the standard language for working with relational databases. Whether you're building a web app, analyzing data, or just starting your programming journey, SQL is one of the most valuable skills you can learn. Primary Key vs Foreign Key — quick example

A Primary Key uniquely identifies each row in a table — like a student ID. A Foreign Key is a column in another table that references that ID, connecting two tables together.

id (PK)first_nameemail
101Rahulrahul@college.test
102Priyapriya@college.test

id is the Primary Key. Another table can reference 101 or 102 using a Foreign Key column, connecting student names to their records.

Sample SQL query

The full guide includes 24 explained SQL commands. Here's a preview of a JOIN query that connects two tables:

SQL
-- Find Rahul's partner using a JOIN
SELECT a.first_name AS student,
       b.first_name AS partner
FROM relationships AS r
JOIN students AS a ON r.student_a_id = a.id
JOIN students AS b ON r.student_b_id = b.id
WHERE r.is_deleted = FALSE;

Result: Rahul | Priya — the JOIN connected the ID numbers to actual names from the Students table.

Part 1

Before SQL, understand the database

1. What is a database?

Imagine this: Your college has hundreds of students. Their names, email addresses, courses and other records cannot just live on random sticky notes. You need an organized place to keep them.

A database is that organized place. It stores information so an application can find and change it reliably.

A table is like a register or spreadsheet inside the database. A database can have many tables.

  • Column = a type of detail, such as first_name.
  • Row = one complete record, such as Rahul's details.
  • Cell = a single value, such as Rahul.

Our Students table

idfirst_nameemail
101Rahulrahul@college.test
102Priyapriya@college.test
103Amanaman@college.test

Here, id, first_name, and email are columns. Each student occupies one row.

2. Primary Key (PK): one unique identity

Imagine this: Two students can both be named Rahul. How do you tell them apart? Give each student a unique ID.

students.id is the Primary Key. It uniquely identifies each student row, and a primary key cannot be NULL.

Remember: A name is not necessarily unique. A student ID is designed to be unique.

3. Foreign Key (FK): connect two tables

Let's make a second table:

Relationships table

idstudent_a_idstudent_b_idrelationship_statusis_deleted
1101102datingfalse

student_a_id = 101 means Rahul. student_b_id = 102 means Priya. But where do those names come from? From the Students table.

  • relationships.student_a_id references students.id.
  • relationships.student_b_id also references students.id.

These two columns are Foreign Keys. They point to primary-key values in another table.

Important: A primary key does not magically become a foreign key. A separate column in another table stores a reference to it.

Mental picture: relationships.student_a_id (101) → students.id (101) → Rahul.

4. What is SQL?

SQL = Structured Query Language. It's the language we use to ask a relational database questions and tell it what to change.

  • “Show me all students” → SELECT.
  • “Add a new student” → INSERT.
  • “Change a relationship status” → UPDATE.
  • “Remove a row” → DELETE.

A query is an instruction sent to the database. Some queries read information; others modify it.

Part 2

Set up a safe practice database

Only run this section in a new, disposable PostgreSQL database. It creates tables and inserts fictional example records. Do not run it against an existing application database without reviewing it.
SQL 
CREATE TABLE students (
  id INTEGER PRIMARY KEY,
  first_name VARCHAR(50) NOT NULL,
  email VARCHAR(120) NOT NULL UNIQUE
);

CREATE TABLE relationships (
  id INTEGER PRIMARY KEY,
  student_a_id INTEGER NOT NULL REFERENCES students(id),
  student_b_id INTEGER NOT NULL REFERENCES students(id),
  relationship_status VARCHAR(20) NOT NULL,
  is_deleted BOOLEAN NOT NULL DEFAULT FALSE,
  ended_at TIMESTAMPTZ,
  CHECK (student_a_id <> student_b_id)
);

INSERT INTO students (id, first_name, email) VALUES
  (101, 'Rahul', 'rahul@college.test'),
  (102, 'Priya', 'priya@college.test'),
  (103, 'Aman', 'aman@college.test');

INSERT INTO relationships
  (id, student_a_id, student_b_id, relationship_status, is_deleted)
VALUES
  (1, 101, 102, 'dating', FALSE);
What just happened? CREATE TABLE made the two registers. PRIMARY KEY makes the student ID unique. REFERENCES students(id) connects the tables. INSERT filled them with example data.

Part 3

Read data with SELECT (DQL)

5. SELECT: “Show me the data”

Imagine this: You walk into the college office and say, “Show me the student register.”
SQL
SELECT * FROM students;
What just happened? SELECT means retrieve data. * means all columns. FROM students tells SQL which table to read.

Expected result: Three rows: Rahul, Priya, and Aman.

Choose only the columns you need

SQL
SELECT id, first_name FROM students;

Why? Sometimes you need names, not email addresses. Selecting only necessary columns also makes queries clearer.

6. WHERE: “Only the student I asked for”

SQL
SELECT * FROM students
WHERE id = 101;
What just happened? WHERE filters rows. Only Rahul's record matches ID 101.

More filtering

SQL
SELECT * FROM students
WHERE first_name = 'Priya';
Remember: Text uses single quotes. Numbers generally don't need them.

7. AND / OR / NOT: combine conditions

SQL
SELECT * FROM students
WHERE id >= 101 AND id <= 102;
What just happened? Both conditions must be true. This returns Rahul and Priya.
SQL
SELECT * FROM students
WHERE first_name = 'Rahul' OR first_name = 'Aman';
What just happened? Either condition can be true.

8. ORDER BY: arrange the results

SQL
SELECT id, first_name FROM students
ORDER BY first_name ASC;
What just happened? Results are alphabetically sorted A → Z. Use DESC for reverse order.

9. LIMIT and OFFSET: show a small page

SQL
SELECT id, first_name FROM students
ORDER BY id
LIMIT 2 OFFSET 0;
What just happened? Returns the first two students. OFFSET 2 would skip those and show the next page. Always choose a stable ORDER BY when paginating.

10. LIKE and ILIKE: search by text

SQL
SELECT * FROM students
WHERE first_name ILIKE 'ra%';
What just happened? PostgreSQL ILIKE searches without caring about letter case. % means “any number of characters.” Rahul matches. Standard LIKE is generally case-sensitive in PostgreSQL.

11. IN and BETWEEN: shorthand filters

SQL
SELECT * FROM students
WHERE id IN (101, 103);
SQL
SELECT * FROM students
WHERE id BETWEEN 101 AND 102;
What just happened? IN matches one of several values. BETWEEN includes both endpoints.

12. IS NULL: missing information

SQL
SELECT * FROM relationships
WHERE ended_at IS NULL;
What just happened? Finds records with no end date. Use IS NULL, not = NULL.

Part 4

Read related data with JOIN

13. JOIN: connect IDs to names

Imagine this: The Relationships table says 101 and 102. You want the actual names, not just numbers. SQL can connect the rows using the foreign keys.
SQL
SELECT
  a.first_name AS student,
  b.first_name AS partner,
  r.relationship_status AS status
FROM relationships AS r
JOIN students AS a ON r.student_a_id = a.id
JOIN students AS b ON r.student_b_id = b.id
WHERE r.id = 1 AND r.is_deleted = FALSE;
Expected result
studentpartnerstatus
RahulPriyadating
What just happened, line by line?
1. FROM relationships AS r starts with the relationship records and gives the table a short nickname, r.
2. JOIN students AS a ON r.student_a_id = a.id finds the student whose ID matches student_a_id.
3. JOIN students AS b ON r.student_b_id = b.id finds the second student.
4. SELECT chooses the names and status to display.
5. WHERE keeps only relationship 1 if it hasn't been soft-deleted.
Remember: A JOIN is a clause used within a SELECT query, not a sixth category of SQL commands.

INNER JOIN vs LEFT JOIN

  • INNER JOIN (plain JOIN) returns rows only when matching records exist on both sides.
  • LEFT JOIN keeps every row from the left table, even if the right table has no match; missing right-side columns become NULL.

Example: list every student, including those with no relationship record:

SQL
SELECT s.first_name, r.id AS relationship_id
FROM students AS s
LEFT JOIN relationships AS r
  ON r.student_a_id = s.id AND r.is_deleted = FALSE
ORDER BY s.id;

Aman will still appear, with a NULL relationship ID. Note that this example checks only student_a_id for simplicity.

Part 5

Change data with DML

14. INSERT: add a new record

Imagine this: A new student joins the college. Add them to the register.
SQL
INSERT INTO students (id, first_name, email)
VALUES (104, 'Neha', 'neha@college.test');
What just happened? A new row was added. In a real app, IDs are often generated automatically rather than typed manually.

15. UPDATE: change existing information

Imagine this: Rahul and Priya break up. Their existing relationship record needs an update.
SQL
UPDATE relationships
SET relationship_status = 'broken_up',
    is_deleted = TRUE,
    ended_at = CURRENT_TIMESTAMP
WHERE id = 1;
What just happened? Only relationship id = 1 changes. Its status now describes the breakup, and is_deleted = TRUE means the application can hide it from its normal active view.
Very important: UPDATE without WHERE can modify every row in the table. Always double-check the filter before running it.

See the updated record

SQL
SELECT id, relationship_status, is_deleted
FROM relationships
WHERE id = 1;

Expected result: 1 | broken_up | true.

16. Soft delete vs hard delete

Soft delete is an application design pattern: instead of removing a row, mark it as hidden/inactive using a flag such as is_deleted.

Normal active view

SQL
SELECT * FROM relationships
WHERE is_deleted = FALSE;

After the breakup update, the example relationship no longer appears.

History view

SQL
SELECT * FROM relationships
WHERE id = 1;

The row still exists. The database didn't forget it.

Hard delete: remove the row

SQL
-- DANGEROUS: removes the row permanently if committed.
-- Shown for learning; do not run unless you intend to delete it.
DELETE FROM relationships
WHERE id = 1;

Difference: Soft delete keeps the record and requires the app to filter it. Hard delete removes the row (subject to transaction rollback, backups, and database retention behavior).

Safety tip: If your application has personal data, keeping history is not always appropriate. Retention and deletion must follow your privacy and legal requirements.

17. DELETE: removing a row is not the same as DROP

SQL
DELETE FROM students
WHERE id = 104;

This deletes Neha's row (if it is not referenced by another row). It does not delete the Students table itself.

Part 6

Count and summarize records

18. COUNT: how many rows?

SQL
SELECT COUNT(*) AS total_students
FROM students;
What just happened? Returns the number of students. If you inserted Neha, the count is four; otherwise it is three.

19. GROUP BY: make groups, then count

SQL
SELECT relationship_status, COUNT(*) AS total
FROM relationships
GROUP BY relationship_status;
What just happened? SQL groups records with the same status and counts each group.

20. HAVING: filter the groups

SQL
SELECT relationship_status, COUNT(*) AS total
FROM relationships
GROUP BY relationship_status
HAVING COUNT(*) >= 1;
What just happened? WHERE filters individual rows before grouping. HAVING filters the summarized groups after grouping.

21. DISTINCT: avoid repeated values

SQL
SELECT DISTINCT relationship_status
FROM relationships;
What just happened? Each unique status appears once.

Part 7

The five common SQL categories

These labels are common teaching conventions. Some sources classify SELECT under DML instead of giving DQL its own category.

CategoryFull formFriendly meaningCommands
DQLData Query Language“Show me something”SELECT
DMLData Manipulation Language“Change the records”INSERT, UPDATE, DELETE
DDLData Definition Language“Build/change the registers”CREATE, ALTER, DROP, TRUNCATE
DCLData Control Language“Who is allowed to do what?”GRANT, REVOKE
TCLTransaction Control Language“Save or undo this set of changes”COMMIT, ROLLBACK, SAVEPOINT

22. DDL: CREATE, ALTER, DROP, TRUNCATE

CREATE makes a new structure. We already used CREATE TABLE in setup.

SQL
ALTER TABLE students
ADD COLUMN enrolled_year INTEGER;
What just happened? We added a new column to the existing Students table.
SQL
-- DESTRUCTIVE examples for understanding only:
-- DROP TABLE students;       -- removes the table structure and data
-- TRUNCATE TABLE students;   -- removes all rows, keeps the table
Do not run these destructive examples in the practice story. Foreign-key references may prevent some operations unless additional steps are taken.

23. DCL: GRANT and REVOKE

Imagine this: A college staff member should be allowed to view records, but not edit them.
SQL
-- Requires an existing role and sufficient privileges.
GRANT SELECT ON students TO college_reader;
REVOKE SELECT ON students FROM college_reader;
What just happened? GRANT gives permission; REVOKE removes that grant. Real-world permissions may also come from other roles.

24. TCL: BEGIN, COMMIT, ROLLBACK

Imagine this: You are testing an update and want a chance to undo it before saving.
SQL
BEGIN;

UPDATE relationships
SET relationship_status = 'dating',
    is_deleted = FALSE,
    ended_at = NULL
WHERE id = 1;

-- Inspect the result before choosing one:
SELECT * FROM relationships WHERE id = 1;

ROLLBACK;
-- Or use COMMIT instead of ROLLBACK to save the change.
What just happened? BEGIN starts a transaction. ROLLBACK cancels changes made in that transaction. COMMIT would save them.

SAVEPOINT: undo just part of a transaction

SQL
BEGIN;
SAVEPOINT before_change;
UPDATE relationships SET is_deleted = FALSE WHERE id = 1;
ROLLBACK TO SAVEPOINT before_change;
COMMIT;
What just happened? The change after the savepoint was undone, but the transaction could still finish.

Part 9

Five beginner mistakes to avoid

1
Forgetting WHERE in UPDATE or DELETE. Without it, you may change or remove every row.
2
Thinking FK values must be different from PK values. A foreign key is supposed to match a referenced key value.
3
Thinking JOIN permanently merges tables. A JOIN combines related rows in a query result; the underlying tables remain separate.
4
Thinking is_deleted = TRUE removes data. It changes a flag; your queries must intentionally exclude those rows.
5
Using = NULL. Use IS NULL or IS NOT NULL.
Bonus: Never concatenate untrusted user input directly into SQL strings. In applications, use parameterized queries to prevent SQL injection.
