Quick differences #

Four pairs that confuse almost everyone at the start.

These twoThe short answer
Git vs GitHubGit is a free program on your computer that saves versions of your project. GitHub is a website that stores a copy of those versions online so you can share them and work with other people.
Commit vs pushA commit saves a version on your computer only. A push sends your commits to GitHub. Until you push, nobody else can see them.
Branch vs fork vs cloneA branch is a separate line of work inside one project. A fork is your own copy of someone else's project on GitHub. A clone is a copy of a project downloaded to your computer.
Pull vs pull requestgit pull downloads new commits and adds them to your work. A pull request is a page on GitHub where you ask the project owner to review your changes and accept them.

Mission 01

What is Git, and why use it? #

Git is a version control system. That means it keeps a history of every saved change in a project folder: what changed, when, and who changed it. You can look back at any saved version and go back to it.

Real-life analogy

Think of save points in a video game. Before a hard level, you save. If things go wrong, you load the save and try again. Git gives your project unlimited save points, and every one has a note saying what you did.

Without Git, most people end up with folders like project-final, project-final-v2 and project-final-REAL. Nobody knows which one is the right one, or what changed between them.

Why people use Git #

  • History: see exactly what changed and when, line by line.
  • Undo: go back to a version that worked when something breaks.
  • Safe experiments: try an idea on a separate branch without touching the working version.
  • Teamwork: several people can work on the same project without overwriting each other.
  • Review: teammates can read your changes before they go live.
  • A copy elsewhere: once you push to GitHub, your history also lives online. It is not a full backup plan, but it helps.
  • Open source: almost every open source project uses Git, so it is how you join in.

Git and GitHub are not the same thing #

Git is the tool. It runs on your computer and works without the internet. You do not need a GitHub account to use it.

GitHub is a website that hosts Git projects (called repositories) online, and adds tools for working together, such as pull requests and issues. GitLab and Bitbucket are similar websites. This guide uses GitHub, but the Git commands are the same everywhere.

Mission 02

How Git thinks: the four places your work lives #

Most Git confusion goes away once you know that your work lives in four places, and that each command moves it from one place to the next.

  • Working directory: your project folder, the files you open and edit. Git notices changes here but does not save them yet.
  • Staging area: a waiting area for your next save. git add puts a change here. You choose exactly what goes into the next commit.
  • Local repository: the saved history, kept in a hidden folder called .git inside your project. git commit saves everything in the staging area here as one new version.
  • Remote repository: a copy of the project somewhere else, usually on GitHub. git push uploads your commits there; git fetch and git pull download other people's commits.

Real-life analogy

Packing a parcel. Your room is the working directory. The box on the table is the staging area: you choose what goes in it. Sealing the box and writing the label is the commit. Handing it to the courier is the push.

Two words you will see a lot #

  • Commit: one saved version of the project, with a message, an author, a date and a unique ID called a hash (for example 252df3a).
  • HEAD: Git's word for "where you are right now". Usually it points to the latest commit on the branch you are working on.

Tip

The single most useful command is git status. It tells you which of these places your changes are in. Run it whenever you are unsure.

Mission 03

Install and set up Git #

Install Git #

  • Windows: download Git for Windows from git-scm.com/downloads. It includes Git Bash, a terminal where every command in this guide works as written. Use Git Bash on Windows.
  • Mac: open the Terminal app and type git --version. If Git is not installed, your Mac offers to install the Command Line Tools, which include Git. You can also run xcode-select --install.
  • Linux: use your package manager. On Ubuntu or Debian: sudo apt install git.

Check that it worked. Your version number may be different; that is fine.

bash
git --version
Output
git version 2.54.0 (Apple Git-157)

Tell Git who you are #

Every commit records a name and an email. Set them once on each computer:

bash
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main

The third line makes new projects start with a branch called main. Older projects, and older tutorials, often use master instead. They work the same way; only the name is different.

Check your settings:

bash
git config --global --list
Output
user.name=Rahul Sharma
user.email=rahul@example.com
init.defaultbranch=main

Note

The email you set is stored inside every commit. On public projects anyone can see it. GitHub can give you a private no-reply address instead: on GitHub, open Settings, then Emails, and turn on Keep my email addresses private. Use the no-reply address it shows in git config.

Logging in to GitHub from the terminal #

You need this before your first push. There are two ways. Pick one.

HTTPS (easiest to start). Your project address looks like https://github.com/you/project.git. GitHub no longer accepts your account password for Git. Instead, use one of these:

  • Git Credential Manager: comes with Git for Windows. It opens a browser window to sign in, then remembers you. On a Mac you can install it with Homebrew.
  • GitHub CLI: install it, run gh auth login, choose HTTPS and say yes when it asks to log in Git with your GitHub account. It saves your login for Git.
  • Personal access token: a long password-like code you create on GitHub. When Git asks for your password, paste the token.

SSH (set up once, then no prompts). Your project address looks like git@github.com:you/project.git. You create a pair of keys: a private key that stays on your computer and a public key you give to GitHub.

bash
ssh-keygen -t ed25519 -C "you@example.com"

Press Enter to accept the default file, and choose a passphrase. Then show the public key (the file ending in .pub), copy it, and add it on GitHub under Settings, then SSH and GPG keys:

bash
cat ~/.ssh/id_ed25519.pub

Test the connection:

bash
ssh -T git@github.com

If it worked, GitHub replies with your username:

Output
Hi USERNAME! You've successfully authenticated, but GitHub does not provide shell access.

"Does not provide shell access" is normal. It only means GitHub does not give you a command line on its servers.

Warning

Never share your private key (the file without .pub) or a personal access token. Do not paste them into chats, screenshots or code. Anyone who has them can push to your projects. If one leaks, delete it on GitHub straight away and make a new one.

Mission 04

Your first repository #

Let us make a real project and save it with Git, one step at a time. Type the commands into your terminal (Git Bash on Windows).

Note

We ran every command in this guide with Git 2.54 in a practice project and copied the output. Your commit IDs, dates and folder paths will be different. Long folder paths are shortened to .../. For the GitHub steps, a local copy stood in for GitHub, so lines that show a GitHub address show the address it would have.

1. Make a folder and look inside it #

bash
mkdir my-first-app
cd my-first-app
git status
Output
fatal: not a git repository (or any of the parent directories): .git

That error is expected. The folder exists, but Git is not watching it yet.

2. Turn the folder into a Git repository #

bash
git init
Output
Initialized empty Git repository in .../my-first-app/.git/

git init creates the hidden .git folder where the history will live. It only works on your computer; it does not create anything on GitHub.

bash
git status
Output
On branch main

No commits yet

nothing to commit (create/copy files and use "git add" to track)

3. Create a file #

bash
printf '# My First App\n' > README.md
git status
Output
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	README.md

nothing added to commit but untracked files present (use "git add" to track)

Untracked means Git sees a new file but is not saving it yet.

4. Stage it, then commit it #

bash
git add README.md
git status
Output
On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
	new file:   README.md

The file is now in the staging area. Save it as the first commit:

bash
git commit -m "Add README with the project name"
Output
[main (root-commit) 252df3a] Add README with the project name
 1 file changed, 1 insertion(+)
 create mode 100644 README.md

252df3a is the short ID (hash) of this commit. root-commit means it is the very first one.

5. Look at the history #

bash
git log
Output
commit 252df3a40f878431ff9d6f64592418a5f8acd65e
Author: Rahul Sharma <rahul@example.com>
Date:   Thu Nov 19 10:00:00 2026 +0530

    Add README with the project name

For a short, one-line view:

bash
git log --oneline
Output
252df3a Add README with the project name

Tip

If git log fills the screen and you cannot type, you are in a viewer. Press q to leave it.

6. Change something and see the difference #

Add a line to README.md and create a new file called index.html (any text editor works). Then:

bash
git status
Output
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   README.md

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	index.html

no changes added to commit (use "git add" and/or "git commit -a")

git diff shows exactly what changed in files Git already tracks. Lines starting with + were added, lines starting with - were removed:

bash
git diff
Output
diff --git a/README.md b/README.md
index 8cc16da..973500c 100644
--- a/README.md
+++ b/README.md
@@ -1 +1,3 @@
 # My First App
+
+A tiny web page to practise Git.

Stage the README and check what is about to be committed with --staged:

bash
git add README.md
git diff --staged
git status --short
Output
M  README.md
?? index.html

In the short view, M means modified and staged, ?? means untracked. (git diff --staged printed the same change as above.) Stage the new file too and commit both:

bash
git add index.html
git commit -m "Add home page and describe the project"
git log --oneline
Output
[main fb4fae0] Add home page and describe the project
 2 files changed, 3 insertions(+)
 create mode 100644 index.html
fb4fae0 Add home page and describe the project
252df3a Add README with the project name

The four states of a file #

StateWhat it meansHow it gets there
UntrackedA new file Git is not saving yetYou create a file
ModifiedA saved file that changed since the last commitYou edit a file
StagedPicked for the next commitgit add
CommittedSaved in the historygit commit

Warning

git add . stages everything in the folder, including files you may not want to share, such as passwords in a .env file or large log files. Run git status first and add files by name until you are comfortable. The .gitignore and secrets section shows how to make Git ignore files for good.

Mission 05

Writing good commits #

A commit message is a note to your future self and your teammates. In six months, git log is how you will find out why something changed.

Keep commits small #

One commit should do one thing: fix one bug, add one section, rename one file. Small commits are easy to understand, easy to review and easy to undo. If your message needs the word "and" twice, it is probably two commits.

How to write the message #

  • First line: a short summary, about 50 characters, that finishes the sentence "This commit will...". For example: Add contact form to home page.
  • Then, if needed: a blank line and a few lines explaining why. The code already shows what changed; the message should say why.

To write a longer message, run git commit without -m. Git opens a text editor; write the summary, a blank line, then the details, save and close.

text
Fix total price on the cart page

The total ignored the delivery charge when the cart had
only one item. Add the charge in every case.

Bad and good examples #

BadBetterWhy
updateUpdate phone number on contact pageSays what changed
fixed stuffFix crash when the email field is emptySays which problem
asdfAdd first draft of the About sectionReadable months later
final changes!!!Shorten home page title for mobileNothing is ever final
login, footer, colours, typoFour separate commitsOne commit, one change

Tip

Some teams start messages with a type, such as feat: add signup, fix: handle empty cart or docs: explain install. This style is called Conventional Commits. It is optional; follow whatever your team uses.

Mission 06

Put your project on GitHub #

So far everything is only on your computer. Now we put a copy on GitHub.

1. Create an empty repository on GitHub #

  1. On GitHub, click the + in the top-right corner and choose New repository.
  2. Give it a name, for example my-first-app, and choose Public or Private.
  3. Do not tick "Add a README", ".gitignore" or "license". Your project already has commits, and starting with an empty repository avoids a clash on the first push.
  4. Click Create repository. GitHub shows the address of your new repository. Copy it.

2. Connect your project and push #

bash
git branch -M main
git remote add origin https://github.com/your-username/my-first-app.git
git remote -v
Output
origin	https://github.com/rahul-example/my-first-app.git (fetch)
origin	https://github.com/rahul-example/my-first-app.git (push)
  • git branch -M main makes sure your branch is called main. If it already is, nothing changes.
  • git remote add origin <URL> saves the GitHub address under the short name origin. "origin" is just the usual name for your main remote; it is not a special GitHub word.

Now upload your commits:

bash
git push -u origin main
Output
To https://github.com/rahul-example/my-first-app.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.

The first time, Git may ask you to log in (see Logging in to GitHub). GitHub may also print a few extra lines starting with Enumerating objects or remote:; that is normal.

-u links your local main to origin/main. From now on, plain git push and git pull know where to go, and git status tells you if you are ahead or behind:

bash
git status
Output
On branch main
Your branch is up to date with 'origin/main'.

nothing to commit, working tree clean

Refresh the page on GitHub: your files and commits are there.

If Git says "remote origin already exists" #

Output
error: remote origin already exists.

You already connected this project to an address. Look at it with git remote -v. If it is wrong, change it instead of adding it again:

bash
git remote set-url origin https://github.com/your-username/my-first-app.git

Warning

Before your first push, check git status for files that must stay private: .env files, passwords, API keys, private keys. Once something is pushed to a public repository, assume someone has copied it. See .gitignore and secrets.

Mission 07

Clone, fetch, pull and push #

A remote is another copy of your repository, usually on GitHub. These four commands move commits between your computer and a remote.

CommandWhat it doesChanges your files?
git cloneDownloads a whole repository, with its history, into a new folderCreates a new folder
git fetchDownloads new commits from the remote, but does not touch your workNo
git pullFetches, then adds those commits to your current branchUsually yes
git pushUploads your new commits to the remoteNo

Clone: get a copy of a project #

bash
git clone https://github.com/rahul-example/my-first-app.git
Output
Cloning into 'my-first-app'...
done.

From GitHub you will also see a few progress lines, such as Receiving objects: 100%. The new folder already has the remote set up as origin:

bash
cd my-first-app
git branch -a
Output
* main
  remotes/origin/HEAD -> origin/main
  remotes/origin/main

remotes/origin/main is Git's memory of what main looked like on GitHub the last time you checked.

Fetch: see what is new, safely #

Say a teammate pushed a commit. git fetch downloads it without changing your files:

bash
git fetch origin
Output
From https://github.com/rahul-example/my-first-app
   fb4fae0..32ff193  main       -> origin/main
bash
git status
Output
On branch main
Your branch is behind 'origin/main' by 1 commit, and can be fast-forwarded.
  (use "git pull" to update your local branch)

nothing to commit, working tree clean

See which commits are waiting:

bash
git log --oneline HEAD..origin/main
Output
32ff193 Add footer line to home page

Pull: bring the new commits into your branch #

bash
git pull --ff-only origin main
Output
From https://github.com/rahul-example/my-first-app
 * branch            main       -> FETCH_HEAD
Updating fb4fae0..32ff193
Fast-forward
 index.html | 1 +
 1 file changed, 1 insertion(+)

Fast-forward means you had no new commits of your own, so Git simply moved your branch forward. --ff-only tells Git to do only that, and to stop rather than mix histories if both sides have new commits.

Real-life analogy

fetch is checking your letterbox and reading the post. pull is reading it and also filing it into your folder.

When you and a teammate both made commits #

This happens all the time in a team. You made a commit, and so did your teammate, on the same branch. Your push is refused:

bash
git push origin main
Output
To https://github.com/rahul-example/my-first-app.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'https://github.com/rahul-example/my-first-app.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.

Git is protecting your teammate's work. If you now run a plain git pull, recent Git versions stop and ask how to combine the two histories:

Output
hint: You have divergent branches and need to specify how to reconcile them.
hint: You can do so by running one of the following commands sometime before
hint: your next pull:
hint:
hint:   git config pull.rebase false  # merge
hint:   git config pull.rebase true   # rebase
hint:   git config pull.ff only       # fast-forward only
hint:
hint: You can replace "git config" with "git config --global" to set a default
hint: preference for all repositories. You can also pass --rebase, --no-rebase,
hint: or --ff-only on the command line to override the configured default per
hint: invocation.
fatal: Need to specify how to reconcile divergent branches.

Nothing is broken. You have three choices:

  • Merge (--no-rebase): keeps both sets of commits and joins them with a merge commit. The simplest choice when you are starting out.
  • Rebase (--rebase): replays your commits on top of your teammate's, for a straight line of history. See Rebase and squash.
  • Fast-forward only (--ff-only): refuses to combine anything. Useful as a safety setting, but in this situation it stops.

To merge:

bash
git pull --no-rebase origin main
Output
From https://github.com/rahul-example/my-first-app
 * branch            main       -> FETCH_HEAD
Merge made by the 'ort' strategy.
 README.md | 2 ++
 1 file changed, 2 insertions(+)
bash
git log --oneline --graph
Output
*   64de4bd Merge branch 'main' of https://github.com/rahul-example/my-first-app
|\  
| * 193a734 Explain how to open the page
* | 4a7c1af Add page title
|/  
* 32ff193 Add footer line to home page
* fb4fae0 Add home page and describe the project
* 252df3a Add README with the project name

Both commits are kept. Now the push works:

bash
git push origin main
Output
To https://github.com/rahul-example/my-first-app.git
   193a734..64de4bd  main -> main

If both of you changed the same lines, Git cannot decide which version to keep and reports a merge conflict. It marks both versions inside the file; you keep the right text, delete the markers, then git add the file and git commit. Read both versions carefully before you delete anything. Step by step in Merging and merge conflicts.

Tip

To make merging the default for every git pull, run git config --global pull.rebase false once. If you would rather decide each time, leave it unset and Git will keep asking.

Warning

You may read online that git push --force fixes a rejected push. It does "fix" it by deleting your teammate's commits from GitHub. Do not use it on a shared branch.

Mission 08

Branches #

A branch is a separate line of work inside one repository. You make a branch, try something on it, and main stays exactly as it was. If the idea works, you merge it in. If it does not, you delete the branch and nothing is harmed.

Real-life analogy

Think of a photocopy of your notes. You scribble, cross out and rewrite on the copy. The original stays clean. When you are happy with the copy, you write the good parts back into the original.

Create a branch and switch to it #

bash
git switch -c feature/contact-page
Output
Switched to a new branch 'feature/contact-page'

-c means "create". Now commit as usual; the commit belongs to the new branch:

bash
git add contact.html
git commit -m "Add contact page"
Output
[feature/contact-page 6c836dd] Add contact page
 1 file changed, 1 insertion(+)
 create mode 100644 contact.html

Switching changes the files you see #

When you switch branch, Git changes the files in your folder to match that branch:

bash
git switch main
ls
Output
Switched to branch 'main'
index.html
README.md
bash
git switch feature/contact-page
ls
Output
Switched to branch 'feature/contact-page'
contact.html
index.html
README.md

contact.html exists only on the feature branch. It is not lost when you go back to main; it is waiting on its own branch.

Tip

Commit or stash your work before switching. If you have unsaved edits that would clash with the other branch, Git refuses to switch and tells you why (see Stash).

See your branches #

bash
git branch
Output
* feature/contact-page
  main

The * marks the branch you are on. git branch -a also lists the branches Git knows about on GitHub.

switch or checkout? #

Older guides use git checkout <BRANCH-NAME> to switch and git checkout -b <BRANCH-NAME> to create. They still work:

bash
git checkout -b feature/old-style
Output
Switched to a new branch 'feature/old-style'

git checkout does many unrelated jobs (it can also restore files), so Git added the clearer git switch for branches and git restore for files. This guide uses the newer commands.

Rename and delete #

You cannot delete the branch you are on, so switch away first:

bash
git switch main
git branch -m feature/login feature/sign-in
git branch -d feature/sign-in
Output
Deleted branch feature/sign-in (was 0060c4e).

-d deletes only a branch whose work is already merged. If it is not, Git stops you:

Output
error: the branch 'feature/contact-page' is not fully merged
hint: If you are sure you want to delete it, run 'git branch -D feature/contact-page'
hint: Disable this message with "git config set advice.forceDeleteBranch false"

That is a safety check. Use capital -D only when you really want to throw that work away.

Put a branch on GitHub #

bash
git push -u origin feature/contact-page

-u links the local branch to the one on GitHub, so later you can just type git push. After it is merged, you can delete the GitHub copy with git push origin --delete <BRANCH-NAME>.

Naming branches #

  • Short, lowercase, words joined with -: feature/contact-page, fix/cart-total, docs/install-steps.
  • No spaces. git switch -c "bad name" fails with fatal: 'bad name' is not a valid branch name.
  • Many teams start with the type of work (feature/, fix/, docs/). Follow your team's habit.

Note

main or master? They are just names. Older repositories often call the first branch master; newer ones, and GitHub's default for new repositories, use main. Commands work the same; type whichever name your repository uses.

Mission 09

Branching strategies #

A branching strategy is simply a team's agreement about which branches exist and how work flows between them. You do not need a complicated one. Here are the common ones, simplest first.

GitHub flow (start here) #

  1. main always works and could be released at any time.
  2. For every change, make a short-lived branch from main: git switch -c fix/cart-total.
  3. Commit, push the branch, and open a pull request.
  4. Someone reviews it. Fix what they find by pushing more commits to the same branch.
  5. Merge the pull request into main and delete the branch.

That is all. It suits solo projects, small teams and most websites and apps.

Trunk-based development #

Everyone merges small changes into main (the "trunk") very often, at least daily. Branches live for hours, not weeks. Unfinished features are hidden behind switches in the code instead of living on long branches. It works well for experienced teams with good automated tests.

Git Flow #

A more formal model with two long-lived branches, main for released versions and develop for ongoing work, plus feature/, release/ and hotfix/ branches. It fits software shipped in numbered versions on a schedule, such as installed apps. For a website that goes live many times a week it is usually more ceremony than you need.

Which should I use? #

SituationGood choice
Learning, or a solo projectGitHub flow
Small team, website or web appGitHub flow
Experienced team that deploys many times a dayTrunk-based
Versioned releases that need long supportGit Flow

Tip

Whatever you choose, the habits that matter most are the same: keep branches short-lived, keep main working, and merge through pull requests so someone else reads the change.

Mission 10

Merging and merge conflicts #

Merging brings the commits from one branch into another. You always merge into the branch you are on, so first switch to the branch that should receive the work, usually main.

bash
git switch main
git merge feature/contact-page

Git does one of two things, depending on what happened on main meanwhile.

Fast-forward: main had no new commits #

Output
Updating c164b68..6c836dd
Fast-forward
 contact.html | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 contact.html

Nothing to combine, so Git just moves main forward to the branch's last commit. The history stays a straight line.

Merge commit: both branches have new commits #

bash
git merge --no-edit feature/footer
Output
Merge made by the 'ort' strategy.
 index.html | 1 +
 1 file changed, 1 insertion(+)

ort is just the name of the method Git uses to combine changes. --no-edit accepts the default message; without it Git opens an editor so you can write one.

bash
git log --oneline --graph -5
Output
*   db64d72 Merge branch 'feature/footer'
|\  
| * 7dc019c Add footer
* | c56a80c Add opening hours to README
|/  
* 6c836dd Add contact page
* c164b68 Add prices section

When the branch is merged, delete it: git branch -d feature/footer.

Merge conflicts #

A conflict happens when both branches changed the same lines of the same file. Git cannot know which version you want, so it asks you. It is normal, not an error in your project.

Here main changed the page title to "The Corner Shop" while the branch changed it to "Oye Nino Shop":

bash
git merge feature/title
Output
Auto-merging index.html
CONFLICT (content): Merge conflict in index.html
Automatic merge failed; fix conflicts and then commit the result.
bash
git status
Output
On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   index.html

no changes added to commit (use "git add" and/or "git commit -a")

Open the file. Git has written both versions into it, between markers:

Output
<<<<<<< HEAD
<h1>The Corner Shop</h1>
=======
<h1>Oye Nino Shop</h1>
>>>>>>> feature/title
<p>Prices</p>
<footer>Made in India</footer>
  • Between <<<<<<< HEAD and ======= is the version on your current branch (main).
  • Between ======= and >>>>>>> feature/title is the version from the branch you are merging.

Fix it in four steps #

  1. Edit the file so it says what it should. Keep one version, the other, or a mix.
  2. Delete all three marker lines (<<<<<<<, =======, >>>>>>>).
  3. Mark the file as fixed: git add index.html
  4. Finish the merge: git commit --no-edit
Output
[main 1f4c75f] Merge branch 'feature/title'

Tip

Code editors such as VS Code highlight conflicts and offer buttons like "Accept Current Change" and "Accept Incoming Change". They do the same four steps for you. Read both versions before you click.

Warning

If a merge goes wrong or you feel lost, run git merge --abort. It puts everything back exactly as it was before you typed git merge. Then try again calmly.

Fewer conflicts #

  • Pull main into your branch often, so differences stay small.
  • Keep branches short-lived and focused on one change.
  • Talk to your team before two people rework the same file.

Mission 11

Rebase and squash #

Rebase is another way to bring a branch up to date. Instead of joining two lines with a merge commit, it lifts your branch's commits off and replays them on top of the latest main, as if you had started your work today. The result is a straight line of history.

You can be productive with Git for years using only merge. Learn rebase when a team asks for it, and follow the one rule below.

Rebase a branch onto main #

Your branch feature/about has two commits. Meanwhile main got a new one:

Output
* 5cf6b23 Add phone number to README
| * f26b5f2 Add founding year to about page
| * 757504a Add about page
|/  
*   1f4c75f Merge branch 'feature/title'
bash
git switch feature/about
git rebase main
Output
Successfully rebased and updated refs/heads/feature/about.
bash
git log --oneline --graph -3
Output
* 9b2f4ba Add founding year to about page
* 48bde00 Add about page
* 5cf6b23 Add phone number to README

Your two commits now sit on top of main, in a straight line. Look closely: their IDs changed (757504a became 48bde00). Rebase does not move commits, it makes new copies of them.

The golden rule #

Warning

Do not rebase commits that you have already pushed to a branch other people use. Because rebase makes new commits, your history no longer matches theirs, and the only way to push it is --force, which can wipe their work. Rebasing your own local commits, or your own feature branch that nobody else uses, is fine.

If you must update a branch you already pushed and you are sure nobody else uses it, use git push --force-with-lease rather than --force. It refuses to overwrite commits on GitHub that you have not seen yet.

Conflicts during a rebase #

Conflicts work like they do in a merge, but you may see one per commit being replayed:

Output
Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
error: could not apply 9f7c8a7... Shorten phone line
hint: Resolve all conflicts manually, mark them as resolved with
hint: "git add/rm <conflicted_files>", then run "git rebase --continue".
hint: You can instead skip this commit: run "git rebase --skip".
hint: To abort and get back to the state before "git rebase", run "git rebase --abort".
  1. Fix the file and remove the markers.
  2. git add README.md
  3. git rebase --continue
Output
Successfully rebased and updated refs/heads/feature/about.

Lost? git rebase --abort returns your branch to how it was before the rebase.

Squash: tidy many small commits into one #

Before opening a pull request you may have commits like "fix typo" and "fix another typo". Squashing combines them into one clean commit.

Option 1: squash when merging. Merge a whole branch as a single commit:

bash
git merge --squash feature/menu
git commit -m "Add menu"
Output
Squash commit -- not updating HEAD
 menu.txt | 3 +++
 1 file changed, 3 insertions(+)
 create mode 100644 menu.txt
[main 3e5a722] Add menu
 1 file changed, 3 insertions(+)
 create mode 100644 menu.txt

The three commits from feature/menu arrive on main as one commit called "Add menu". GitHub's Squash and merge button on a pull request does the same thing.

Option 2: interactive rebase. To clean up your own branch before pushing it:

bash
git rebase -i HEAD~3

Git opens an editor with your last three commits, oldest first, followed by help lines that start with #:

Output
pick b0c1214 # Shorten phone line
pick c54fd7f # fix typo
pick 1ef99fc # fix another typo

Change pick to fixup on the lines you want folded into the commit above them, then save and close:

text
pick b0c1214 # Shorten phone line
fixup c54fd7f # fix typo
fixup 1ef99fc # fix another typo
Output
Successfully rebased and updated refs/heads/feature/about.

The three commits are now one. Use squash instead of fixup if you also want to edit the combined message. The golden rule applies here too: only for commits you have not shared.

Merge or rebase? #

MergeRebase

Mission 12

Branch vs fork vs clone #

These three words all mean "a copy", which is why they are confusing. The difference is where the copy lives and why you make it.

What it isWhere it livesUse it when
BranchA separate line of work inside one repositoryInside the same repositoryYou can push to the project and want to work without touching main
ForkYour own copy of someone else's repositoryOn GitHub, under your accountYou cannot push to the project, for example open source
CloneA full copy of a repository, with historyOn your computerYou want to work on any repository locally

They work together. To contribute to someone else's project you fork it, clone your fork, make a branch, then open a pull request.

Contribute to an open source project, step by step #

Rahul wants to add a recipe to Priya's project priya-example/recipes. He cannot push to it, so he forks it.

1. Fork it on GitHub. On the project page, click Fork (top right), choose your account as the owner and click Create fork. You now have your-username/recipes.

2. Clone your fork (not the original):

bash
git clone https://github.com/rahul-example/recipes.git
cd recipes

3. Connect the original project so you can fetch its updates. By convention it is called upstream:

bash
git remote add upstream https://github.com/priya-example/recipes.git
git remote -v
Output
origin	https://github.com/rahul-example/recipes.git (fetch)
origin	https://github.com/rahul-example/recipes.git (push)
upstream	https://github.com/priya-example/recipes.git (fetch)
upstream	https://github.com/priya-example/recipes.git (push)

origin is your fork, which you can push to. upstream is the original, which you only fetch from.

4. Make a branch and commit your change:

bash
git switch -c add-chai-recipe
git add chai.md
git commit -m "Add masala chai recipe"

5. Push the branch to your fork:

bash
git push -u origin add-chai-recipe
Output
To https://github.com/rahul-example/recipes.git
 * [new branch]      add-chai-recipe -> add-chai-recipe
branch 'add-chai-recipe' set up to track 'origin/add-chai-recipe'.

6. Open a pull request. On GitHub, your fork shows a Compare & pull request button. The base repository is Priya's project and the head is your branch. See Pull requests.

Keep your fork up to date #

The original project keeps moving. Bring its new commits into your copy before starting new work.

On GitHub: open your fork, click Sync fork above the file list, then Update branch.

On the command line:

bash
git switch main
git fetch upstream
git merge upstream/main
git push origin main
Output
From https://github.com/priya-example/recipes
 * [new branch]      main       -> upstream/main
Updating 1dcb874..78cb329
Fast-forward
 lassi.md | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 lassi.md
To https://github.com/rahul-example/recipes.git
   1dcb874..78cb329  main -> main

Tip

Never commit directly to main in your fork. Keep it as a clean copy of the original, and do every change on its own branch. Syncing then never causes conflicts.

Mission 13

Pull requests and code review #

A pull request (PR) is a page on GitHub that says: "here are the changes on my branch, please review them and merge them into main." It shows every changed line, lets people comment, and keeps a record of why the change was made.

Note

A pull request is not the same as git pull. git pull downloads commits to your computer. A pull request is a request on GitHub for someone to merge your work.

Open a pull request #

  1. Push your branch: git push -u origin <BRANCH-NAME>.
  2. On the repository page, GitHub shows a yellow banner with Compare & pull request. Click it. (Or open the Pull requests tab and click New pull request.)
  3. Check the two branches at the top. base is where the changes should go, usually main. compare is your branch.
  4. Write a clear title and description (see below).
  5. Click Create pull request. Not ready yet? Use the arrow next to it and choose Create draft pull request.

With the GitHub CLI you can do the same from the terminal with gh pr create.

Write a description people want to review #

text
Add contact page

What: a new contact.html with the shop's phone number and
opening hours, linked from the home page footer.

Why: customers kept asking for the phone number on Instagram.

How to test: open the home page, click Contact in the footer.

Closes #12
  • Say what changed and why. Add screenshots for anything visual.
  • Keep it small. A pull request that changes 50 lines gets a careful review; one that changes 2,000 gets a quick "looks fine".
  • Writing Closes #12 links the pull request to issue number 12. When the pull request is merged into the default branch, GitHub closes the issue automatically. Fixes and Resolves work too.

Draft pull requests #

A draft pull request shares unfinished work without asking for a formal review. It cannot be merged. When it is ready, click Ready for review. Drafts are great for "is this the right direction?" questions early on.

Reviewing #

Reviewers read the Files changed tab, comment on specific lines, and finish with one of three choices:

ReviewMeans
CommentGeneral feedback, without approving or blocking
ApproveThe changes are ready to merge
Request changesSomething must be fixed before merging

To answer review comments, just commit to the same branch and push. The pull request updates itself; you do not open a new one.

Tip

When you review, be specific and kind: "This breaks if the cart is empty; could we check for that?" beats "wrong". When you are reviewed, remember the comments are about the code, not about you.

The three merge buttons #

ButtonWhat happensPick it when
Create a merge commitKeeps every commit and adds a merge commitYou want the full history
Squash and mergeCombines all the pull request's commits into oneThe branch has many small "fix typo" commits
Rebase and mergeAdds each commit on top of the base branch, no merge commitYou want a straight history and clean commits

Not every repository shows all three; the owner can turn options off in the settings.

After the merge #

bash
git switch main
git pull
git branch -d <BRANCH-NAME>

Bring the merged work into your local main and delete your local copy of the branch. GitHub offers a Delete branch button on the merged pull request for the GitHub copy.

Note

After Squash and merge or Rebase and merge, git branch -d may say the branch "is not fully merged". That is because GitHub made new commits instead of reusing yours. If the pull request shows as merged on GitHub, it is safe to delete with git branch -D <BRANCH-NAME>.

Mission 14

Undo mistakes safely #

Almost every mistake in Git can be fixed. The trick is to pick the right command, because some of them throw work away. Read this table before you try anything.

SituationCommandRisk
See what is going ongit status, git diffNone, read only
Took a file out of the next commit, keep the editsgit restore --staged <file>Low
Throw away unsaved edits to one filegit restore <file>Edits are gone for good
Fix the last commit's message or add a forgotten file (not pushed yet)git commit --amendChanges the commit ID
Undo the last commit, keep the changes stagedgit reset --soft HEAD~1Rewrites local history
Undo the last commit, keep the changes as editsgit reset HEAD~1Rewrites local history
Undo the last commit and throw the changes awaygit reset --hard HEAD~1Destructive
Undo a commit that is already on GitHubgit revert <COMMIT-HASH>Safe, adds a new commit
Find a commit you "lost"git reflogNone, read only

HEAD~1 means "one commit before where I am now".

Unstage a file, keep your edits #

You ran git add on a file by mistake, for example a .env file with a password:

bash
git status --short
Output
A  .env
bash
git restore --staged .env
git status --short
Output
?? .env

The file is out of the staging area and untracked again. Your file is untouched.

Throw away edits to one file #

bash
git status --short
Output
 M index.html
bash
git restore index.html
git status --short

Nothing is printed: index.html is back to how it was in the last commit.

Warning

git restore <file> cannot be undone. The edits were never committed, so Git has no copy of them. If you might want them later, commit them or use git stash first.

Fix the last commit #

Spotted a typo right after committing?

bash
git log --oneline -1
Output
84b577e Updte README
bash
git commit --amend -m "Update README"
Output
[main f714afb] Update README
 Date: Thu Nov 19 12:00:00 2026 +0530
 1 file changed, 1 insertion(+)

To add a forgotten file to the same commit, git add it first, then run git commit --amend --no-edit. Notice the ID changed from 84b577e to f714afb: amend makes a new commit. Only amend commits you have not pushed yet.

Undo the last commit with reset #

git reset moves your branch back to an earlier commit. The three modes differ in what happens to the changes from the commits you undo:

ModeThe commitIts changes
--softUndoneKept, still staged
(default, called mixed)UndoneKept as edits, not staged
--hardUndoneThrown away
bash
git reset --soft HEAD~1
git status --short
Output
A  a.txt
bash
git reset HEAD~1
git status --short
Output
?? a.txt

Warning

git reset --hard deletes uncommitted work and moves your branch. Never use it as a general "fix everything" button. And do not reset commits you have already pushed to a shared branch; use git revert instead.

Undo a commit that is already on GitHub: revert #

git revert does not delete anything. It adds a new commit that does the opposite of the old one, so everyone's history stays the same and you can push normally:

bash
git revert --no-edit HEAD
Output
[main 9a06eeb] Revert "Add a.txt"
 Date: Thu Nov 19 12:00:00 2026 +0530
 1 file changed, 1 deletion(-)
 delete mode 100644 a.txt

Use the hash of any commit instead of HEAD to revert an older one. Without --no-edit, Git opens an editor so you can write why you reverted.

The safety net: reflog #

Git keeps a private diary of where your branch has pointed, called the reflog. It can rescue commits after a bad reset. Here a reset --hard removed the "Add price list" commit:

bash
git log --oneline
Output
8e19b6a Start the shop project
bash
git reflog
Output
8e19b6a HEAD@{0}: reset: moving to HEAD~1
234e2fa HEAD@{1}: commit: Add price list
8e19b6a HEAD@{2}: commit (initial): Start the shop project

The lost commit is 234e2fa. Go back to it:

bash
git reset --hard 234e2fa
Output
HEAD is now at 234e2fa Add price list

Note

The reflog only lives on your computer and old entries expire after a while. It can bring back commits. It cannot bring back edits that were never committed.

Mission 15

Stash: put work aside for later #

You are halfway through something when you need to switch branch, perhaps to fix an urgent bug. Your edits are not ready to commit, and Git will not let you switch:

bash
git switch feature/about
Output
error: Your local changes to the following files would be overwritten by checkout:
	README.md
Please commit your changes or stash them before you switch branches.
Aborting

Stash puts your unfinished edits on a shelf and gives you a clean folder. Later you take them back.

Real-life analogy

Sweeping the papers on your desk into a drawer so you can use the desk for something else, then pulling them back out exactly as they were.

Put work aside and bring it back #

bash
git stash
Output
Saved working directory and index state WIP on main: 3e5a722 Add menu
bash
git status --short

Nothing is printed: the folder is clean. Switch branch, fix the bug, commit, come back. Then:

bash
git stash pop
Output
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   README.md

no changes added to commit (use "git add" and/or "git commit -a")
Dropped refs/stash@{0} (522e91e13a70dc27a112a099bcc9d1edb5584ca3)

Your edits are back, and the stash entry is removed.

Give stashes a name #

With more than one stash, plain "WIP" is hard to tell apart. Add a note:

bash
git stash push -m "WIP: new welcome text"
git stash list
Output
Saved working directory and index state On main: WIP: new welcome text
stash@{0}: On main: WIP: new welcome text

Useful stash commands #

CommandWhat it does
git stashStash changes to tracked files
git stash push -u -m "<NOTE>"Also stash new (untracked) files, with a note
git stash listShow all stashes; the newest is stash@{0}
git stash popBring back the newest stash and remove it from the list
git stash applyBring back the newest stash but keep it in the list
git stash dropDelete the newest stash

Warning

By default git stash leaves new files behind, because Git is not tracking them yet. Use git stash push -u to include them. And do not use stash as long-term storage: stashes are easy to forget and are never pushed to GitHub. For anything you want to keep, make a commit on a branch.

If popping a stash clashes with changes made since, you get a normal conflict. Fix it the same way as a merge conflict; the stash is kept until you drop it.

Mission 16

Tags and releases #

A tag is a permanent label on one commit, such as v1.0.0. Branches move forward with every commit; a tag stays where you put it. Teams tag the exact commit that was released, so they can always find it again.

Create a tag #

bash
git tag -a v1.0.0 -m "First public version"
git tag
Output
v1.0.0

-a makes an annotated tag, which stores who made it, when, and a message. Without -a and -m you get a lightweight tag, just a name. Use annotated tags for releases.

bash
git show v1.0.0 --stat
Output
tag v1.0.0
Tagger: Rahul Sharma <rahul@example.com>
Date:   Thu Nov 19 15:40:00 2026 +0530

First public version

commit 3e5a72298df68bf438b344dcba5c0e47e80e9893
Author: Rahul Sharma <rahul@example.com>
Date:   Thu Nov 19 15:40:00 2026 +0530

    Add menu

 menu.txt | 3 +++
 1 file changed, 3 insertions(+)

To tag an older commit, add its hash: git tag -a v0.9.0 <COMMIT-HASH> -m "<NOTE>".

Push tags to GitHub #

git push does not send tags. Push them on purpose:

bash
git push origin v1.0.0
Output
To https://github.com/rahul-example/recipes.git
 * [new tag]         v1.0.0 -> v1.0.0

git push origin --tags pushes every tag you have that GitHub does not.

Delete a tag #

bash
git tag -d v1.0.1-light
Output
Deleted tag 'v1.0.1-light' (was 3e5a722)

That removes it only on your computer. For one already on GitHub, also run git push origin --delete <TAG-NAME>. Avoid moving or deleting a released tag; people may already depend on it.

Version numbers #

Most projects use semantic versioning, MAJOR.MINOR.PATCH:

  • PATCH (1.0.0 to 1.0.1): bug fixes only.
  • MINOR (1.0.1 to 1.1.0): new features that do not break anything.
  • MAJOR (1.1.0 to 2.0.0): changes that break how people used the old version.

Releases on GitHub #

A GitHub release is built on a tag. It adds a title, release notes and downloadable files, and appears on the right side of the repository page. Open Releases, click Draft a new release, pick your tag, write what changed and publish.

Mission 17

.gitignore and secrets #

Some files should never go into Git: passwords, downloaded libraries, logs and build output. A file called .gitignore in the top folder of your project lists them, and Git then acts as if they are not there.

Before adding a .gitignore, Git offers to track everything:

bash
git status --short
Output
?? .env
?? debug.log
?? node_modules/

Create a file named .gitignore with these lines:

gitignore
node_modules/
.env
*.log
  • node_modules/ ignores a whole folder (downloaded JavaScript packages; anyone can reinstall them).
  • .env ignores one file, the usual place for passwords and API keys.
  • *.log ignores every file ending in .log.
bash
git status --short
Output
?? .gitignore

The ignored files have gone from the list. Commit the .gitignore itself so everyone on the project uses the same rules. To check why a file is ignored:

bash
git check-ignore -v .env
Output
.gitignore:2:.env	.env

That means: line 2 of .gitignore is the rule that hides .env.

Tip

GitHub can add a ready-made .gitignore for your language when you create a repository, and it keeps a collection of templates at github.com/github/gitignore.

A file was already committed #

.gitignore only affects files Git is not tracking yet. If .env is already committed, adding it to .gitignore does nothing. Stop tracking it like this (the file stays on your computer):

bash
git rm --cached .env
git commit -m "Stop tracking .env"
Output
rm '.env'
[main 9f19d16] Stop tracking .env
 1 file changed, 1 deletion(-)
 delete mode 100644 .env

If you committed a secret #

Warning

If a password, API key or token was ever committed, and especially if it was pushed, treat it as leaked. First revoke or change it on the service it belongs to. Removing the file in a new commit does not remove it from the history; anyone can still find the old version. Cleaning history is a separate, careful job: follow GitHub's guide Removing sensitive data from a repository.

Mission 18

Debugging with Git #

Something broke, and you want to know what changed, when, and who changed it. Git's history can answer all three. In this example, the cart's delivery charge has quietly become zero.

Look through the history #

bash
git log --oneline
Output
3da18bf Add contact line
fee0355 Mention free delivery in README
cd5a2f6 Offer free delivery
46c962c Add README
d3b05f9 Set up project notes
52f17f0 Add cart total

Narrow it down:

CommandShows
git log --oneline -- cart.jsOnly commits that changed cart.js
git log --oneline --author="Priya"Only commits by one person
git log --oneline --since="2026-11-14"Only commits after a date
git log -p -1 -- cart.jsThe latest change to cart.js, with the exact lines

Search for when a line appeared: log -S #

-S finds the commits that added or removed a piece of text:

bash
git log --oneline -S "delivery = 0"
Output
cd5a2f6 Offer free delivery

See what a commit changed: show #

bash
git show --stat cd5a2f6
Output
commit cd5a2f671cdf4b12bee09676f9b12daf92209909
Author: Priya Nair <priya@example.com>
Date:   Sat Nov 14 11:00:00 2026 +0530

    Offer free delivery

 cart.js | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)

Leave out --stat to see the changed lines themselves.

Who last changed each line: blame #

bash
git blame cart.js
Output
^52f17f0 (Rahul Sharma 2026-11-11 11:00:00 +0530 1) const price = 100;
cd5a2f67 (Priya Nair   2026-11-14 11:00:00 +0530 2) const delivery = 0;
^52f17f0 (Rahul Sharma 2026-11-11 11:00:00 +0530 3) const total = price + delivery;

Each line shows the commit, the author and the date it last changed. (^ marks the very first commit.) Despite the name, use it to find context, not someone to blame: open the commit and read why the change was made. On GitHub, open a file and click Blame for the same view.

Find the commit that broke it: bisect #

When you do not know where to look, git bisect finds the guilty commit by halving the history each step. You only answer "good" or "bad".

bash
git bisect start
git bisect bad
git bisect good 52f17f0

bad means "the current commit is broken". good 52f17f0 names a commit you know worked.

Output
status: waiting for both good and bad commits
status: waiting for good commit(s), bad commit known
Bisecting: 2 revisions left to test after this (roughly 1 step)
[46c962c9bee412bf58fbe1aa7c8e413ddb559a3d] Add README

Git has checked out a commit in the middle. Test it (here: is the delivery charge still 40?) and tell Git:

bash
git bisect good
Output
Bisecting: 0 revisions left to test after this (roughly 1 step)
[fee0355479f25cf9f524ea88a2e8ee9e25476f76] Mention free delivery in README

Keep answering git bisect good or git bisect bad. In this example two more answers (bad, then bad) are enough:

Output
cd5a2f671cdf4b12bee09676f9b12daf92209909 is the first bad commit
commit cd5a2f671cdf4b12bee09676f9b12daf92209909
Author: Priya Nair <priya@example.com>
Date:   Sat Nov 14 11:00:00 2026 +0530

    Offer free delivery

Always finish with:

bash
git bisect reset

That returns you to the branch you started on.

Tip

If a command can test for the bug, Git can do all the answering for you: git bisect run <COMMAND>. Git treats exit code 0 as good and most other codes as bad. With 1,000 commits, bisect needs only about 10 steps.

Mission 19

Common errors and fixes #

Git's messages look scary but they almost always say what to do next. Read the whole message, including the hint: lines. Below are the ones beginners meet most, with the exact text Git prints.

fatal: not a git repository #

Output
fatal: not a git repository (or any of the parent directories): .git

Meaning: you are not inside a Git project folder. Fix: cd into your project folder, or run git init if this folder should become one.

pathspec did not match any files #

Output
fatal: pathspec 'nosuchfile.txt' did not match any files

Meaning: the file name is wrong, or you are in a different folder. Fix: run ls and git status and copy the exact name. Names are case-sensitive on many systems.

nothing to commit, working tree clean #

Output
On branch main
nothing to commit, working tree clean

Meaning: not an error. Either nothing changed, or you saved the file in a different folder. If you expected changes, check that your editor saved the file and that you are in the right project.

src refspec main does not match any #

Output
error: src refspec main does not match any
error: failed to push some refs to 'https://github.com/rahul-example/my-first-app.git'

Meaning: you tried to push a branch that does not exist yet. Usually you have not made a first commit, or your branch is called master. Fix: check with git branch and git log. Make a commit first, or push the branch name you actually have.

Push rejected #

Output
 ! [rejected]        main -> main (non-fast-forward)
error: failed to push some refs to 'https://github.com/rahul-example/my-first-app.git'
hint: Updates were rejected because the tip of your current branch is behind
hint: its remote counterpart. If you want to integrate the remote changes,
hint: use 'git pull' before pushing again.

You may also see (fetch first) instead of (non-fast-forward). Meaning: GitHub has commits you do not. Fix: git pull --no-rebase origin main, fix any conflicts, then push again. Do not use --force on a shared branch. Full walkthrough in Clone, fetch, pull and push.

You have divergent branches #

Output
hint: You have divergent branches and need to specify how to reconcile them.
fatal: Need to specify how to reconcile divergent branches.

Meaning: both you and GitHub have new commits, and Git wants you to choose how to combine them. Fix: git pull --no-rebase to merge (simplest), or git pull --rebase. To stop the question for good: git config --global pull.rebase false.

refusing to merge unrelated histories #

Output
fatal: refusing to merge unrelated histories

Meaning: the two sides share no common commit. This usually happens when you created a repository on GitHub with a README, and also ran git init and committed locally. Fix: if you are sure both belong together, git pull --no-rebase --allow-unrelated-histories origin main, then push. Next time, create the GitHub repository empty.

Your local changes would be overwritten #

Output
error: Your local changes to the following files would be overwritten by checkout:
	README.md
Please commit your changes or stash them before you switch branches.
Aborting

Meaning: switching branch would destroy your unsaved edits, so Git stopped. Fix: commit them, or git stash, switch, and git stash pop later. See Stash.

CONFLICT (content): Merge conflict #

Output
CONFLICT (content): Merge conflict in index.html
Automatic merge failed; fix conflicts and then commit the result.

Meaning: both sides changed the same lines. Fix: see Merging and merge conflicts. To back out: git merge --abort.

The branch is not fully merged #

Output
error: the branch 'experiment' is not fully merged

Meaning: deleting this branch would lose commits that exist nowhere else. Fix: merge it first, or, if you really want to throw it away, git branch -D experiment.

You are in 'detached HEAD' state #

Output
Note: switching to 'HEAD~1'.

You are in 'detached HEAD' state. You can look around, make experimental

Meaning: you are looking at an old commit instead of a branch. Fix: to go back, git switch main. If you made commits here that you want to keep, first save them on a branch: git switch -c <BRANCH-NAME>.

error: remote origin already exists #

Output
error: remote origin already exists.

Meaning: this project is already connected to an address. Fix: check it with git remote -v, and change it with git remote set-url origin <REPOSITORY-URL>.

Permission denied (publickey) #

Output
Permission denied (publickey).
fatal: Could not read from remote repository.

Meaning: you are using an SSH address, and GitHub did not accept a key from your computer. Fix: test with ssh -T git@github.com. Check ssh-add -l lists a key, and that the matching .pub key is added on GitHub under Settings, then SSH and GPG keys. Do not use sudo with Git. See Install and set up Git.

HTTPS asks for a password, then fails #

Meaning: GitHub no longer accepts your account password for Git over HTTPS. Fix: sign in with Git Credential Manager or gh auth login, or paste a personal access token when Git asks for the password. See Install and set up Git.

Repository not found #

Output
remote: Repository not found.
fatal: repository 'https://github.com/rahul-example/my-frist-app.git/' not found

Meaning: the address has a typo (here frist), the repository was renamed, or it is private and you are not signed in as someone with access. GitHub says "not found" for private repositories too, so it does not reveal that they exist. Fix: copy the address again from the green Code button on GitHub, then git remote set-url origin <REPOSITORY-URL>. If it is private, check you are signed in with the right account.

Mission 20

Useful GitHub features #

GitHub is more than a place to store code. These are the features worth knowing first. Plans and settings change over time, so follow the links to GitHub Docs for the current details.

README #

A file called README.md in the top folder is shown on the repository's front page. Say what the project is, how to run it, and how to help. It is written in Markdown: # for headings, - for bullet points, backticks for code.

Issues #

Issues are GitHub's to-do list and bug tracker: "plan, discuss, and track work". Each issue has a number, such as #12. Writing Closes #12 in a pull request description closes the issue when the pull request is merged into the default branch. About issues

Pull requests and reviews #

The heart of working together on GitHub. See Pull requests and code review.

Protecting main #

Under the repository's Settings, branch protection rules and rulesets let the owner protect important branches: for example require a pull request and an approving review before merging, or block force pushes and deletion. Which options you get depends on your plan and whether the repository is public. About protected branches

GitHub Actions #

Actions run tasks automatically when something happens, for example run your tests on every pull request, or deploy when main changes. Each workflow is a YAML file in the .github/workflows folder of your repository. Understanding GitHub Actions

GitHub Pages #

Free hosting for static websites (HTML, CSS and JavaScript) straight from a repository. On the free plans, the repository must be public. Pages sites are public on the internet even when the repository is private. What is GitHub Pages?

Releases #

A release packages a tagged version with notes and files to download. See Tags and releases.

Secret scanning and push protection #

GitHub can spot passwords, keys and tokens in code. Push protection for your personal account is on by default and stops you from pushing secrets to public repositories. Treat it as a safety net, not a plan: keep secrets out of Git with .gitignore. About push protection

GitHub CLI #

gh brings GitHub to your terminal. A few examples:

CommandWhat it does
gh auth loginSign in, and set up Git to use that sign-in
gh repo createCreate a GitHub repository
gh repo forkFork a repository
gh pr createOpen a pull request for the current branch

Mission 21

Best practices and common mistakes #

Habits that save you #

  • Run git status constantly. Before you add, before you commit, before you switch, when anything feels odd.
  • Commit small and often. One change per commit, with a message that says what and why. Small commits are easy to review and easy to undo.
  • Pull before you start work each day, and push when you stop. Small, frequent syncs mean small conflicts.
  • One branch per change. Keep main working. Delete branches after merging.
  • Read the diff before committing. git diff --staged catches debug code, stray files and passwords.
  • Use pull requests, even alone. Reading your own changes on GitHub the next morning catches mistakes.
  • Set up .gitignore on day one, before the first git add ..

Git rarely loses committed work. When something goes wrong, stop, run git status and git log --oneline, and read the messages. Calm beats clever.

Mission 23

Practice mission and knowledge check #

Reading is not enough; Git clicks when your hands have done it. This mission uses only commands from this guide and takes about 30 minutes.

Your mission #

  1. Create a folder called git-practice, run git init, and check git status.
  2. Create README.md with one line about yourself. Stage it and commit: Add README.
  3. Create an empty repository on GitHub (no README) and push your project with git push -u origin main.
  4. Make a branch feature/hobbies. Add a file hobbies.md with three hobbies. Commit and push the branch.
  5. On GitHub, open a pull request from feature/hobbies into main. Read the Files changed tab, then merge it.
  6. Back in your terminal: git switch main, git pull, and delete the local branch.
  7. Make a conflict on purpose. On a new branch change the first line of README.md and commit. Switch to main, change the same line differently and commit. Merge the branch, fix the conflict, and commit.
  8. Make a commit with a typo in the message, then fix it with git commit --amend.
  9. Make a commit, push it, then undo it safely with git revert. Push again.
  10. Run git log --oneline --graph and explain each line to yourself.

If you finish all ten, you know more Git than many people who use it every day.

Knowledge check #

Answer in your head, then check below.

  1. You ran git commit. Can your teammate see the commit on GitHub?
  2. What is the difference between git fetch and git pull?
  3. You want to contribute to a project you cannot push to. What do you do first?
  4. Which is safe for a commit already pushed to a shared branch: git reset or git revert?
  5. Your push is rejected with "fetch first". What happened and what do you do?
  6. What does git restore --staged <file> do to your edits?
  7. You need to switch branch but your work is half done. Name two options.
  8. Where do the conflict markers come from, and what must you do with them?

Answers #

  1. No. A commit is saved only on your computer until you git push.
  2. fetch downloads new commits but does not change your files or branch. pull fetches and then merges them into your current branch.
  3. Fork it on GitHub, then clone your fork, make a branch, push, and open a pull request.
  4. git revert. It adds a new commit that undoes the old one, so nobody's history changes.
  5. Someone pushed commits you do not have. Run git pull, fix any conflicts, then push.
  6. Nothing. It only takes the file out of the next commit; your edits stay in the file.
  7. Commit the work on its branch, or git stash it and git stash pop later.
  8. Git writes them when both sides changed the same lines. Keep the right text, delete all the marker lines, then git add and commit.

Questions people ask #

What is Git?

Git is a free program that keeps a history of every saved change in a project folder. Each saved version is called a commit. You can see what changed, when and by whom, and go back to an earlier version at any time. It works on your own computer, without the internet.

What is the difference between Git and GitHub?

Git is the tool on your computer that records versions of your project. GitHub is a website that stores a copy of Git projects online, so you can back them up, share them and work with other people through pull requests and reviews. You can use Git without GitHub; GitLab and Bitbucket are similar websites.

How do I push my code to GitHub?

Create an empty repository on GitHub and copy its address. In your project folder, run git remote add origin <REPOSITORY-URL> once, then git push -u origin main. After that, git add, git commit and git push send new work. A commit alone stays on your computer until you push.

What is the difference between a branch and a fork?

A branch is a separate line of work inside one repository, used to build a feature without touching the main version. A fork is your own copy of someone else's repository on GitHub, used when you cannot push to the original, for example to contribute to an open source project. A fork can have many branches.

What is a pull request?

A pull request is a page on GitHub where you ask to merge the changes from one branch into another. Teammates can read the changes, comment and approve before anything is merged. It is not the same as git pull, which downloads new commits to your computer.

How do I undo a commit safely?

If the commit is already on GitHub, use git revert <COMMIT-HASH>. It adds a new commit that reverses the old one and is safe on shared branches. If you have not pushed yet, git reset HEAD~1 removes the last commit and keeps your changes as edits. Avoid git reset --hard unless you are sure you want the changes gone.
